From the inspected source and mounted TreeDX library snapshot, the SDK is a single published ESM TypeScript package whose job is to define portable TreeSeed contracts plus typed remote clients, not to own server execution or product workflows. That matches both the project library README at `/workspace/.treedx/library/README.md` and the repository README at `README.md`, which describe `@treeseed/sdk` as the portable contract and remote API package for TreeSeed and TreeDX.

The codebase is organized as one repo-level package rather than a monorepo workspace. The root manifest in `package.json` exports many explicit subpaths and keeps publication scoped to `README.md` and `dist/`. The source tree under `src/` is grouped by platform boundary:
- `src/operator-contracts`, `src/content`, `src/knowledge`, `src/feedback`, `src/graph`, `src/security`, `src/deployment`, `src/development`, `src/site-contracts`, and `src/standards` define wire contracts and compatibility surfaces.
- `src/treedx`, `src/treeai`, `src/capacity-provider`, and `src/entrypoints/clients` provide typed remote client facades.
- `src/agent-capacity`, `src/capacity`, `src/types`, `src/sdk-types`, and `src/model-registry` hold shared agent, capacity, and schema primitives.
- `scripts/` contains the release, verification, standards, and build tooling.
- `tests/contract` and `tests/unit` hold the focused verification suites.

That boundary is reinforced by `README.md`, which explicitly says the package does not own persistence, scheduling, repository mutation, content publication, deployment, provider runtimes, or server-side workflows. The CI pipeline in `.github/workflows/verify.yml` also treats this as a contract package: it installs dependencies, runs `npm run verify:direct`, then packs and seals the artifact.

On linting: there is no standalone ESLint, Biome, Prettier, or xo configuration in the inspected repo root, and the root search did not surface any `.eslintrc*`, `eslint.config.*`, or `biome.*` files. Instead, the package defines `"lint": "npm run build:dist"` in `package.json`. So the current “lint” step is effectively a build gate, not a rules-based style linter. The real verification stack is broader:
- `package.json`: `verify:direct` runs `release:verify`.
- `package.json`: `release:verify` runs `check:file-lengths`, `check:file-architecture`, and `scripts/packages/release-verify.ts`.
- `tsconfig.json`: strict TypeScript compilation is enabled (`"strict": true`).
- `vitest.contracts.config.ts`: Vitest drives the focused contract and unit suites.
- `.github/workflows/verify.yml`: CI executes `npm run verify:direct`, not a separate ESLint/Biome job.

So the practical linting/setup answer is: this repo currently relies on TypeScript strictness, custom verification scripts, and contract tests as its quality gate, with `npm run lint` acting as a build alias rather than a conventional static-style linter.
