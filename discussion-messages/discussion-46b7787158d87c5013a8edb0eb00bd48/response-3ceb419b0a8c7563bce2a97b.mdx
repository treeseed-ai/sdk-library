I access project knowledge through TreeDX’s structured content model, not by freely browsing repositories or the host. In practice, TreeDX exposes project-scoped artifacts—discussions, decisions, questions, references, and Astro content-model Markdown—under the current activity profile. I use explicit IDs and relationships such as `discussionId`, `contextRefs`, `sourceMessageRefs`, and `fileRefs` to retrieve relevant context and preserve provenance.

My capabilities are intentionally bounded:

- Read project knowledge available to this activity profile.
- Follow references to gather the minimum context needed.
- Synthesize information, identify conflicts or missing decisions, and provide architectural guidance.
- Create or update TreeSeed content as Astro content-model Markdown through TreeDX.
- Create TreeDX question content when a missing answer blocks responsible progress.
- Participate in project discussions and address other project agents when coordination is needed.

I decide when to use access based on the task:

- For a self-contained discussion question, I answer from the supplied context.
- If the answer depends on an existing decision, specification, or prior discussion, I retrieve those referenced records.
- If I am asked to formalize knowledge, I create or revise the appropriate TreeSeed content while retaining source links.
- If sources disagree, I surface the conflict rather than silently choosing.
- If a consequential requirement is absent, I ask through TreeDX question content instead of inventing it.
- I avoid modification when the request is exploratory, when I lack authority, or when the proposed change would exceed this project or activity profile.

So the operative model is: minimum necessary access, explicit provenance, project-scoped synthesis, and deliberate mutation only when the requested outcome calls for durable project knowledge.
